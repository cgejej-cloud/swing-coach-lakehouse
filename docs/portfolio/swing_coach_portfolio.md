# 스크린골프 스윙 티칭 서비스 + 오픈소스 레이크하우스 (개인 프로젝트)

**2026.10** · 기획·데이터 엔지니어링·ML·백엔드 전담 · 오픈소스 전용, 데스크탑 1대

## 배경과 과제

스크린골프는 샷 결과(구질·비거리)와 스윙 영상(나스모)을 **따로** 보여준다. 슬라이스가 났다는 건 알 수 있지만 *왜* 났는지, 연습이 *효과가 있는지*는 알 수 없다.

- **원인과 결과의 분리** — 영상(원인)과 구질(결과)이 연결되지 않음
- **기록의 단절** — 샷 하나씩만 보여서 누적 패턴을 볼 수 없음
- **제약** — 정면 카메라 1대(측면 지표 측정 불가), 데스크탑 1대(RAM 16GB), 오픈소스만 사용

영상을 순서대로 올리면 샷마다 짧은 티칭 카드가 쌓이고, 누적 데이터로 "내 나쁜 샷의 원인"을 찾는 서비스와, 이를 받치는 레이크하우스를 만들었다. 데이터: 본인 스윙 영상 201개(45라운드, 192개 고유), 영상별 클럽·구질·비거리 라벨.

## 전체 아키텍처

```
 [앱 · Windows]                              [플랫폼 · WSL2 Docker]

 업로드(이어 올리기, 1MB 청크)                 Postgres ─WAL─▶ Debezium ─▶ Kafka ─▶ 스트림 소비자(마이크로배치)
   → Postgres (영상 = 작업 큐, SKIP LOCKED)  ─┘                                    │ 키별 최신 상태, 같은 타입 계약
   → 워커: MediaPipe 포즈 → 구간 감지 → 지표 14개                                  ▼
         → 클럽 판별(MobileNetV3) → 카드 규칙        Trino ──MERGE / DELETE(행 해시)──▶ Iceberg silver (Lakekeeper)
   → 피드 카드 (기준 스윙 겹침 그림 + 메시지)              │                              ▲ 오프셋은 레이크 커밋 후 커밋
                                                    ├──▶ dbt: gold 4개 + 테스트
   포즈 프레임(파일) ── 배치 ──▶ SeaweedFS raw/landing  └──▶ ops: 실행 이력 · 품질 검사 · 스트림 배치
   누적 분석 화면 ◀──── gold 조회      Airflow 야간: 배치 대조(차이 0건 확인) → dbt 원천 테스트 → Iceberg 유지보수
```

## 설계 판단 — 왜 이렇게 만들었나

**수정일시 증분이 아니라 행 내용 해시 MERGE**

앱 DB에는 믿을 만한 수정 시각이 없다. 실무에서 원천이 수정일시를 갱신하지 않아 증분 적재가 5개년치 변경을 조용히 놓친 경험이 있어, 처음부터 수정 시각에 의존하지 않기로 했다. 원천 전체 스냅샷을 착지 구역에 parquet로 떨구고, silver는 행 내용 해시(xxhash64)가 달라진 행만 `MERGE`한다. 원천에서 사라진 키는 삭제한다.

**품질 검사는 건수 + 값 합계 + 무결성 = 오류, 타당성 = 경고**

"건수는 맞는데 금액이 틀린" 장애를 실무에서 겪었기 때문에 건수 대조만으로는 부족하다고 봤다. 지표 합계 대조, 키 유일성, 참조 무결성은 실패 시 실행 전체를 실패시키고, 측정값 타당성(템포 범위 등)은 경고로 기록한다. 단, 앱이 신뢰하는 데이터에서 타당성 위반이 나오면 오류로 올린다.

**측정할 수 없는 것은 말하지 않는다**

정면 카메라에서 탑의 왼팔은 카메라를 향해 2D 각도가 왜곡된다(드라이버 중앙값 40°, 아이언 116°로 일관성 없음). "탑에서 왼팔이 잘 펴져 있어요(35°)" 같은 틀린 문장이 나와 지표에서 제외했다. 구간 감지 신뢰도가 낮거나 몸 크기 추정이 비정상이면 지적 자체를 생략한다.

**오케스트레이터는 나중에**

WSL 메모리 7GB에 Trino(2.6GB)가 올라가 있고 단계가 5개뿐이라, Airflow 대신 순차 실행 스크립트 + 실행 로그 테이블(`ops.pipeline_runs`)로 시작했다. 스케줄·재시도 요구가 생기는 시점에 전환한다.

## Case 1 — 정답 없이 튜닝하던 구간 감지를 정답 30개로 보정

- **문제** — 손 높이 궤적으로 탑·임팩트를 잡았는데 템포 분포가 0.8~36:1로 퍼짐. 정답이 없어 "비현실적 값이 적은 설정"으로 고르고 있었음
- **분석** — P1~P10 정의와 템포 측정 연구(백스윙 약 0.73초, 다운스윙 약 0.26초)를 기준으로, 영상 30개(드라이버·아이언 각 15)의 구간을 프레임 단위로 표시해 정답 세트 구축(AI 보조 라벨링, ±2~3프레임). 비교해 보니 **탑을 항상 약 6프레임(0.1초) 이르게** 잡고 있었음 — 탑에서 손이 머리 뒤로 가려져 높이 추정이 흔들린 탓
- **해결** — 탑을 "평활화한 궤적에서 최고점 근처 6% 구간의 마지막 프레임"으로 재정의, 설정 24가지를 정답에 대해 그리드 서치
- **결과** — 탑 평균 오차 **5.7 → 1.7프레임**(±3 이내 3% → 93%), 템포 오차 1.26 → 0.54
- **판단 근거** — 측정 방법을 고칠 때는 먼저 정답부터 만든다. 정답 없는 튜닝은 "그럴듯한 분포"를 맞출 뿐 맞는 값을 보장하지 않는다

## Case 2 — 첫 업로드에서 터진 스키마 드리프트

- **증상** — 앱에서 처음 업로드한 영상이 처리된 뒤 자동 동기화가 실패. `MERGE table column types don't match`
- **원인** — 업로드 영상은 나스모 번호·구질·홀이 없어(NULL) pandas가 정수 열을 실수로 추론. 반대로 첫 적재 때 전부 NULL이던 `club_conf`는 문자열로 silver 테이블이 생성되어 있었음
- **해결** — ① 착지 단계에 열 타입 계약(정수·실수 열 고정) ② silver 타입이 계약과 다르면 해당 테이블만 착지 스냅샷에서 재구축(Iceberg는 varchar→double 변경 불가) ③ Iceberg에 없는 tinyint는 integer로 저장되므로 드리프트에서 제외 — 이걸 놓쳐 매 실행 재구축되며 멱등성이 깨지는 2차 문제도 잡음
- **결과** — 재구축 후 품질 검사 22/22, 재실행 변경 0건. 계약은 단위 테스트로 고정
- **판단 근거** — 타입 추론은 데이터가 바뀌면 같이 바뀐다. 파생 계층은 언제든 다시 만들 수 있게 두고, 원천 쪽 계약으로 흔들림을 막는다

## Case 3 — 수정일시 없이 바뀐 값 1건을 잡는지 검증

- **시나리오** — 원천에서 영상 1건의 비거리를 수정 시각 갱신 없이 168 → 169m로 변경
- **결과** — 다음 실행에서 **그 1건만** 갱신, 값 합계 검사 통과, Iceberg 스냅샷으로 시점별 값 조회(168 → 169 → 원복 168). 같은 입력 재실행은 변경 0건
- **의미** — 실무에서 증분 적재가 놓친 유형의 변경을 구조적으로 막는다는 것을 재현 실험으로 확인

## Case 4 — 클럽 판별 83% → 93.5%, 그리고 "모르면 말하지 않기"

- **문제** — 업로드 영상은 클럽 정보가 없어 자동 판별 필요. 자세 특징 모델이 드라이버 영상을 아이언으로 판별해 "스탠스가 넓어요(공 12개)"라는 틀린 카드를 만듦
- **분석** — 드라이버는 공을 티 위에 올리고 헤드가 크다. 어드레스 장면의 공·헤드 영역을 잘랐는데 처음엔 정확도가 그대로 → 직접 이미지를 확인하니 **잘라낸 영역에 공이 없었음**(위에서 비스듬히 찍어 공이 발목보다 한참 아래). 영역을 고친 뒤에도 원본 픽셀은 매장별 조명·매트 색에 흔들림
- **해결** — ImageNet 사전학습 MobileNetV3 임베딩 + 자세 특징 + 로지스틱 회귀(데이터 168개라 미세조정 대신 전이 학습). 확신도 0.8 미만은 판정 보류
- **결과** — 5-fold 교차검증 **82.7% → 91.1%**. 이후 한 프레임 대신 어드레스 3프레임(약 0.1~0.4초 전) 임베딩을 평균해 **93.5%**, 확신도 0.8 이상만 판정하면 샷 93%를 **95.5%**로 목표 95% 달성(같은 분할에서 설정을 고른 만큼 약간 낙관적). 문제의 영상도 드라이버(확신도 1.0)로 판별
- **판단 근거** — 틀린 지적은 지적 없음보다 나쁘다. 정확도 하나가 아니라 "얼마나 판정하고 그때 얼마나 맞는지"로 설계했다

## Case 5 — 배치에서 CDC 스트림으로: 같은 코드, 대조로 검증

- **문제** — 전체 스냅샷 배치는 업로드가 레이크에 닿기까지 배치 주기를 기다려야 하고, 데이터가 늘면 매번 전체를 다시 읽는다. 앱 DB가 SQLite라 변경 로그를 흘려보낼 수도 없었다
- **설계** — 앱 DB를 Postgres로 옮기고(ID 유지, 건수 검증, 작업 큐는 `SKIP LOCKED`) Debezium → Kafka → 직접 만든 소비자로 연결. 소비자는 Iceberg 싱크 커넥터 대신 **배치와 같은 변환·타입 계약·해시·MERGE 함수**를 쓴다. 키별 마지막 상태만 반영하고, **레이크 커밋이 끝난 뒤에만 Kafka 오프셋을 커밋**
- **검증** — 기존 데이터 569 이벤트를 흘려도 변경 0건(배치와 해시 일치). 앱 API 변경 2.5초, 수정일시 없는 변경·삽입·삭제 약 4.5초 만에 Iceberg 반영. 배치 대조는 차이 0건
- **장애 주입** — 레이크 반영 후 오프셋 커밋 직전에 프로세스를 죽이고 재시작 → 같은 이벤트 1건이 재전달되고 MERGE 결과 변경 0건. 처음에는 재시작한 소비자가 아무것도 읽지 못했는데, 죽은 소비자가 세션 타임아웃(45초) 동안 파티션을 쥐고 있었기 때문 → 타임아웃 단축, 파티션 할당 전엔 대기로 세지 않도록 수정
- **운영** — gold는 dbt가 소유(모델 4개 + 테스트 19개)하고, Airflow가 매일 대조 → dbt 원천 테스트 → Iceberg 유지보수(작은 파일 병합, 스냅샷 만료)를 돌린다. WSL VM과 Windows 시계가 11초 달라 지연이 음수로 찍힌 것도 같은 시계끼리 비교하도록 고쳤다
- **판단 근거** — 실시간 경로를 새로 만들 때 가장 위험한 건 "배치와 조용히 다른 결과"다. 두 경로가 같은 함수를 쓰게 하고, 배치를 대조 작업으로 남겨 스트림을 매일 검증하게 했다. 실무에서 Snowpipe를 보류했던 이유(원천 구조상 중복)와 같은 문제를 멱등 MERGE와 커밋 순서로 풀었다

## 분석 결과 — 내 슬라이스의 원인 후보

드라이버 슬라이스 샷(13개)은 스트레이트 샷(40개)보다 **탑에서 골반이 오른쪽으로 밀리는** 경향이 뚜렷했다(효과 크기 −1.1, Mann-Whitney p=0.004). 구간 감지를 보정한 뒤에도 유지된 결과이며, 드라이버 카드에서 가장 많이 나온 지적과도 일치한다. 인과가 아닌 상관이고 한 사람의 데이터라는 한계를 카드 문구에도 반영했다("이 패턴이 클 때 슬라이스가 더 많았어요 (내 샷 54개 분석)").

## 사용 기술

Python, FastAPI, PostgreSQL, Debezium, Apache Kafka, Apache Iceberg, Trino, Lakekeeper, SeaweedFS, dbt, Apache Airflow, MediaPipe(Pose, Image Embedder), OpenCV, scikit-learn, SciPy, Docker(WSL2), pyarrow, pytest

## 다시 설계한다면

- **원천을 처음부터 Postgres로** — SQLite로 시작해 전체 스냅샷 배치를 먼저 붙였고, CDC를 위해 나중에 이전했다. 처음부터 Postgres였다면 이전 작업 없이 CDC를 바로 붙일 수 있었다. 다만 배치를 먼저 만든 덕에 스트림을 검증할 대조 기준이 생겼다
- **정답 세트를 먼저** — 구간 감지를 정답 없이 먼저 튜닝한 시간이 결국 재작업이 됐다
