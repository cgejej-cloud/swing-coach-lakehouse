# ADR 001 — 데스크탑 1대 위 레이크하우스 구성

- 상태: 채택 (2026-10-07)
- 맥락: WSL2 VM 메모리 7GB, Windows 11 데스크탑 1대. 앱 원천은 SQLite(영상 = 작업 큐), 포즈 프레임 142만 행.

## 결정

| 영역 | 선택 | 대안 | 이유 |
|---|---|---|---|
| 객체 저장소 | SeaweedFS (Apache-2.0) | MinIO | MinIO 커뮤니티판은 2025년부터 바이너리 배포 축소·유지보수 모드 |
| 테이블 포맷 | Apache Iceberg | Delta | 엔진 중립, Trino·Spark·PyIceberg 모두 지원, 스냅샷 타임 트래블 |
| 카탈로그 | Lakekeeper (REST, Postgres) | Hive Metastore, JDBC 카탈로그 | 표준 REST 카탈로그, 컨테이너 256MB 이내 |
| 엔진 | Trino 단일 노드 (힙 2GB) | Spark | 적재·변환·조회를 SQL 하나로, 메모리 예측 가능 |
| 원천 착지 | parquet 전체 스냅샷 → `raw/landing/<table>/latest` + `dt=` 보관 | CDC, 수정일시 증분 | 원천에 신뢰할 변경 시각이 없음. 규모가 작아 전체 스냅샷이 싸고 재처리가 쉬움 |
| 변경 감지 | 행 내용 해시(xxhash64) + `MERGE` | 수정일시 기준 증분 | 수정일시가 안 바뀐 변경을 놓친 실무 경험(포트폴리오 Case 4). 해시는 값 변경을 항상 잡음 |
| 삭제 | 전체 스냅샷 대비 사라진 키 `DELETE` | soft delete | 단일 사용자, 원천이 진실 |
| 품질 | 건수 + **값 합계** + 키 유일성 + 참조 무결성 = error, 타당성 = warn | 건수만 | 건수는 맞는데 값이 틀린 장애를 잡기 위해 |
| 오케스트레이션 | `pipeline/run.py` (순차 실행 + 실행 로그 테이블) | Airflow | 7GB 안에서 Trino와 동시 실행 부담. 단계가 5개라 DAG 도구 이득이 작음 → 스케줄·재시도가 필요해질 때 Airflow로 전환 |

## 검증 (2026-10-07)

- 첫 실행: 5개 테이블, 포즈 142만 행 적재 37초. 재실행: **변경 0건** (멱등).
- 원천 값 1건을 수정일시 없이 변경 → **변경 1건만 반영**, 값 합계 검사 통과, Iceberg 스냅샷으로 변경 전 값 조회 가능.
- 품질 검사가 구간 감지 오류 4건(다운스윙 1~2프레임)을 경고로 잡음 → 앱에서도 이미 신뢰도 '낮음'으로 지적 생략.

## 결과와 한계

- 앱(Windows)은 SQLite를 계속 쓰고, 레이크하우스는 분석·이력용. 앱 DB를 Postgres로 옮기는 것은 다중 사용자 단계에서.
- 전체 스냅샷 방식은 데이터가 커지면 비싸짐 → 그때 영상 단위 증분(업로드 이벤트) + Kafka로 전환 검토.
