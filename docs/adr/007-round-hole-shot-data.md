# ADR 007 — 라운드 · 홀 · 샷 데이터 (제안)

- 상태: 채택 (2026-10-14 제안, 2026-10-15 구현) — 최근 10라운드 적재
- 맥락: 지금 레이크하우스는 "영상 1개 = 샷 1개" 단위다. 점수가 어디서 새는지는 볼 수 없다.
  2026-10-14 라운드(88타)를 손으로 분석해 보니 +16 중 7타가 벌타, 그중 6타가 파5 롱샷(130~190m)이었다.
  골프존 스코어카드에는 홀별 타수·퍼트·벌타, 홀 상세보기의 **모든 샷**(비거리·남은 거리·떨어진 곳), 최근 10라운드 드라이버 낙하 좌표가 있다.

## 목표 질문

1. 파3/4/5별로 몇 타를 잃나, 그중 벌타는 몇 타인가
2. 남은 거리 구간(예: 130~190m)별 그린 적중률과 벌타율 → "여기서는 레이업"
3. 드라이버 좌우 분산이 라운드마다 어떻게 변하나 (평소 왼쪽 미스, 큰 미스는 어느 쪽)
4. **스윙 판정(정석 기준)이 그 홀 결과와 관련 있나** — 영상 카드와 홀 성적을 잇는 연결

## 데이터 흐름

```
골프존 웹 (로그인된 내 브라우저)
  └─ 수집기: 라운드 1개 = JSON 1개 (스코어카드 + 18홀 샷 + 드라이버 낙하 + 샷 분석 요약)
       data/golfzon/rounds/{pg_code}.json      ← 원본 그대로 보관 (재처리 가능)
  └─ pipeline/extract.py: raw.landing.golfzon_* (parquet, 타입 계약)
  └─ transform.upsert(): Iceberg silver MERGE (행 해시, 멱등)
  └─ dbt gold + 테스트 → 앱 누적 분석 · "내 데이터에 묻기"
Airflow: 기존 DAG에 golfzon 적재 태스크 추가 (새 JSON이 있을 때만)
```

- **수집 방식**: 골프존 내부 API를 쿠키로 직접 호출하지 않는다(로그인 정보를 다루게 되고 사이트 변경에 취약).
  사용자의 로그인된 브라우저에서 페이지가 이미 받은 데이터를 읽어 JSON으로 저장한다. 수집 절차는 공개하지 않는다.
  - 처음에는 페이지가 로컬 앱(`127.0.0.1`)으로 바로 보내게 했지만, Chrome이 공개 사이트 → 로컬 주소 요청을 권한 확인에 묶어 두었다.
    그 권한을 대신 허용하지 않고, 페이지 안에 만든 JSON을 나눠 읽어 저장하는 방식으로 바꿨다. 수신 엔드포인트와 CORS 설정은 지웠다.
- **CDC가 아닌 배치**: 앱 DB 변경이 아니라 라운드 단위 파일이 들어오는 것이라 기존 배치 경로(착지 → MERGE)를 쓴다.

## Silver 테이블

| 테이블 | 키 | 주요 열 |
|---|---|---|
| fact_round | pg_code | course, played_at, mode, strokes, putts, penalties, fairway_pct, gir_pct (골프존 계산값) |
| fact_hole | pg_code, hole_no | course_part, hole_in_part, par, strokes, putts, penalties, score_to_par, tee_lie |
| fact_hole_shot | pg_code, hole_no, shot_no | start_lie, start_remain_m, distance_m, end_remain_m, lie_code, lie, is_penalty_lie, is_relocation, swing_no, x, y |
| fact_driver_landing | pg_code, hole_no | x_m(+오른쪽), y_m, attr — 여러 라운드 페이지에 겹쳐 나오므로 키로 중복 제거 |
| (연결) | — | 영상의 session_key = pg_code, hole = hole_no 로 바로 조인된다. 별도 테이블 없이 gold `swing_vs_hole`에서 연결 |

`start_remain_m`은 직전 샷의 남은 거리(1번 샷은 홀 길이)로 만든다 → "어디서 친 샷인가"가 생긴다.

## Gold (dbt)

| 모델 | 답하는 질문 |
|---|---|
| par_type_summary | 파별 평균 타수, 잃은 타수, 벌타 |
| shot_outcome_by_distance | 남은 거리 구간별 그린 적중률 · 벌타율 · 다음 샷 남은 거리 |
| driver_dispersion | 라운드별 평균 좌우, 표준편차, 페어웨이율, 큰 미스 방향 |
| swing_vs_hole | 카드 판정(잘함/보통/아쉬움) × 티샷 결과(페어웨이·러프·벌타) × 홀 스코어 |

## 샷 목록 읽는 법 (10라운드에서 확인)

- 행 하나 = 공이 멈춘 곳: (비거리, 홀까지 남은 거리, 위치 코드, x, y). 다음 샷의 출발 거리는 직전 행의 남은 거리.
- 벌타는 스윙 없이 공을 옮기는 행으로 나온다: 패널티 구역 뒤 **드롭존**(27), OB 뒤 **프런트티**(13), 또는 OB 뒤 **직전 위치를 다시 찍은 행**(위치 코드는 평범한 페어웨이 등).
  이 세 경우를 `is_relocation`으로 두면 **180홀 전부에서 스코어카드 벌타 수와 일치**했다.
- 위치 코드 12종: 1 페어웨이, 2 러프, 3 그린, 4 벙커, 5 그린벙커, 6 패널티, 8 홀인, 9 OB, 10 에이프런, 13 프런트티, 23 헤비러프, 27 드롭존. 파일마다 본 코드의 이름도 같이 저장한다.
- 드라이버 낙하 attr 코드는 문서가 없어서 같은 티샷의 위치와 맞춰 봤다: 0 페어웨이, 1 러프, 2 벙커, 3 OB, 4 패널티, 5 기타 — 145개 전부 일치.
- 파6 홀이 있었다(735m). 파 범위 검사는 3~6.

## 데이터 품질 (실제 데이터에서 본 것)

- 샷 목록 수와 타수가 항상 같지는 않다: 익산 2H는 10타인데 목록은 9줄(마지막 퍼트가 빠짐), OB 뒤에는 같은 거리 샷이 다시 나온다.
  → `strokes = 목록 샷 수 + 빠진 퍼트` 대조는 **경고**로 두고, 홀 타수는 스코어카드 값을 정답으로 쓴다.
- 퍼트 수 = 그린에서 시작한 샷 수 (경고), 벌타 수 = 패널티/OB 착지 수 (경고)
- 키 유일성 · par 3~6 · 라운드별 홀 완전성 · 퍼트 ≤ 타수 (오류)

## 결과 (2026-10-15, 최근 10라운드)

| 항목 | 값 |
|---|---|
| 적재 | 라운드 10 · 홀 180 · 샷 864 · 드라이버 낙하 145, 배치 실행 50초, 품질 검사 38개 중 실패 0 |
| 샷 목록 대 스코어카드 | 179/180홀 일치, 1홀은 마지막 퍼트 누락(경고) |
| 파별로 잃은 타수 | 파4 102홀 +79(벌타 18) · 파5 38홀 +46(벌타 10) · 파3 39홀 +18 |
| 남은 거리별 그린 적중 | 100~130m 46% → 130~160m 27% → 160~190m 14% → 190~220m 7%(벌타 구역 13%) |
| 드라이버 | 라운드 평균 좌우 퍼짐 ±20~30m, 10라운드 중 7번 평균이 왼쪽. 벌타 비율 0~33% |
| 스윙 판정 × 홀 결과 | 연결된 드라이버 영상 22개 — 판정별 차이를 말하기엔 적다 |
| 내 데이터에 묻기 | 새 테이블 질문 8개(프롬프트 예시와 겹치지 않게 따로 만든 평가셋) 4/8. 기존 15문항은 12 → 11/15: 프롬프트가 길어지자 "골프존 라운드 수"에서 source 조건을 빠뜨림 |

- 추가 수집은 같은 방법으로 라운드 단위. 각 페이지가 최근 10라운드 드라이버 낙하를 보여 주므로 과거 라운드를 모으면 낙하 기록도 함께 채워진다.

## 하지 않는 것

- 골프존 사이트 구조가 바뀌면 수집기는 깨진다. 원본 JSON을 보관하므로 파이프라인과 과거 데이터는 영향 없음.
- 다른 사람(동반자) 데이터는 수집하지 않는다.
